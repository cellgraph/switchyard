# Workflow state and recovery

The controller owns transitions among `awaiting_review`, `review_running`, `fixing`, `validating`, `ready_for_human`, `escalated`, and `stopped`. Transition commands take explicit evidence and persist the resulting state and an append-only reason/head-SHA record together. Agent output is not a transition command.

Readiness requires an explicit `completed_clean` review for the current head, a known non-empty configured required-check set, and a passing snapshot for every configured check at that exact SHA. Missing, stale, pending, failed, unknown, or indeterminate evidence fails closed. A new head clears current review and check evidence; if validation is active, the workflow remains `validating` until its cycle outcome is recorded. The validation-start SHA is persisted so a review on a changed head can be distinguished from stale evidence even when review arrives before the cycle outcome. An unsuccessful validation below the limit returns to `fixing`, allowing another attempt from the current findings even when no new head exists. A validation-successful fix remains pending until reviewed; if that review finds issues, the attempt counts as unsuccessful. Three unsuccessful fix/review cycles escalate the workflow.

SQLite migrations are tracked in `schema_migrations`. Webhook delivery IDs are unique. A delivery left `processing` at restart returns to `pending`; handlers must use durable operation IDs for any external side effect because the process may have acted before it recorded completion. Pending operations at restart become `ambiguous`, are never replayed automatically, and cause their workflows to escalate. An operator or later reconciliation policy can resolve them explicitly. No state transition approves or merges a pull request.

The store uses Node.js `node:sqlite` and synchronous bounded transactions for the single local controller. The GitHub inbox records an attempt count and the next retry time for failed reconciliation. A closed PR stops the workflow and clears active review and check evidence. The store records GitHub closure as the stop source so that an authoritative reopen can restore `awaiting_review` while preserving the fix-cycle count. Reopening waits for any pending external operation to finish, and an ambiguous operation escalates even when GitHub closed the PR. Operator stops and escalations stay terminal. Databases from Phase 1 retain their existing stop behavior because those rows have no GitHub closure source.
