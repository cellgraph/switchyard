# ADR-0006: Orchestrate through native tools

- Status: Accepted architectural direction. Implementation pending.
- Date: 2026-11-25
- Baseline: `e0b10d6`, the merge of PR #21

## Context

After PR #21 merged, the operator reviewed the architecture against the principle of choosing the simplest solution that satisfies current requirements. Switchyard needs deterministic coordination, durable workflow state, exact-head review and CI evidence, and a human handoff. The all-local setup made early development convenient. Filesystem checkpoints, runtime fingerprints, approval gates, and controller-owned publication were architectural choices made during that development. Their presence in the code does not establish a product requirement.

## Decisions

1. **Orchestration boundary and deployment.** Switchyard coordinates agents, tools, and external systems through supported native interfaces. It tracks execution and workflow history, evaluates outcomes, and asks for operator intervention when needed. Git, GitHub, and agent runtimes own their native functions. The operator owns the integrity, credentials, and permissions of execution environments. Add mechanisms only when a demonstrated orchestration requirement calls for them. Run a persistent controller on a VM with agents on configured local or remote hosts. Continue to support convenient local development.
2. **GitHub event delivery.** Use webhooks as the primary trigger for GitHub activity. A delivery signals that authoritative GitHub state may have changed. Webhook notifications, startup, periodic sweeps, and explicit operator requests invoke one shared reconciliation implementation. Reconsider the durable webhook inbox and separate delivery-processing paths. The workflow depends on current GitHub state and tolerates missed, duplicated, or out-of-order notifications.
3. **Git-native source state.** Git and GitHub are authoritative for changes, commits, branches, and worktrees. Consume Git-native evidence relevant to workflow decisions and allow ordinary agent and operator interaction with worktrees. Drop recursive filesystem hashes, ignored-file checkpoints, and their size and entry limits. Dependencies, build artifacts, caches, and other environmental state belong to the execution host.
4. **Native sessions.** Keep the provider session identifier and execution context needed to request continuation through supported interfaces. The provider manages its sessions and determines whether continuation works, including after ordinary upgrades or configuration changes. Drop direct provider-internal database reads, transcript hashing, transcript filesystem identity checks, and comprehensive runtime configuration fingerprints. Handle an unsuccessful continuation as an execution outcome under workflow policy. Leave provider-internal state to the provider.
5. **Workflow policy.** Authorize workflows through rules that establish triggers, success criteria, stopping conditions, and when operator judgment is needed. A configured repository can enroll all eligible PRs automatically. An operator can also explicitly start implementation of Plan 002, after which the workflow proceeds under its rules. Neither path requires routine approvals for each instance or step. Pause when the rules call for operator judgment. Defer a general-purpose workflow language and elaborate authorization or delegation machinery until a concrete requirement warrants them. Switchyard never merges a PR automatically.
6. **Agent-owned implementation, validation, and publication.** Agents implement changes, run appropriate tests and validation, commit, and push. Switchyard coordinates the work and observes native agent results, Git, and GitHub. Retire controller staging, candidate sealing, publication commits, custom push mechanisms, and duplicate validation. Start with role-specific instructions and task prompts. A repository-level `SWITCHYARD.md` referenced from `AGENTS.md` is an option for standing instructions.
7. **Implementation scope.** Give the Implementer the assignment and relevant scope, and rely on engineering judgment about necessary changes. Drop mandatory allowed-path lists. Independent review provides accountability for unrelated or unnecessary changes. The operator manages environmental controls and native permissions.
8. **Review content in GitHub.** GitHub owns review text, findings, comments, discussions, and detailed dispositions. SQLite retains coordination metadata and references as needed, including review identity, reviewed commit, execution status, finding identity, and disposition status. Agents retrieve substantive content from GitHub and publish their findings, disposition explanations, and implementation responses there. Retire the dedicated review-content publication and synchronization subsystem and the redundant permanent copy of review text. Handle unavailable external evidence under workflow policy, including pausing when required.
9. **Conservative recovery.** Reconcile and continue when an authoritative system establishes the outcome. Retry within workflow limits when an operation is known not to have executed. Pause for inspection and operator intervention when the outcome remains uncertain. Use native session inspection and continuation when appropriate. Add recovery mechanisms when operational experience demonstrates a need.
10. **Explicit placement.** Configure each role's worker, provider, model, and native runtime profile. If the configured worker is unavailable, wait. Dynamic selection, generalized capability negotiation, load balancing, automatic failover, and session migration are outside the current design. Keep the transport and lifecycle mechanisms needed to execute work and reconsider protocol complexity against explicit placement and conservative recovery.

SQLite remains the controller's durable state store. The controller makes deterministic transitions, records workflow and execution history, and evaluates exact-head review and CI evidence. PR readiness requires explicit clean review and passing required checks for the current head. Missing review comments never establish a clean review. Merge remains a human decision.

## Consequences

- At the PR #21 baseline, the controller still uses the durable inbox and explicit approval gates, controller-local fixes still validate and publish through the controller, and the worker still checkpoints files and provider state. Remote execution still supports standalone review turns through capability matching and leases. See the [architecture implementation status](../architecture.md#current-implementation-after-pr-21) and linked operating guides.
- Unavailable GitHub content may require a pause. Native runtime failures and uncertain effects may require operator inspection. Workflow records preserve the status, references, and reason for the decision.
- [Plan 002](../plans/002-claude-code-authentication.md) needs revision before implementation. Revisit its exact runtime and transcript bindings, ignored-file review checks, mandatory path gate, controller publication assumptions, and distributed acceptance checks. The native authentication investigation remains useful.
- [Plan 001](../plans/001-pr-review-loop.md) needs revision for the follow-up after Phase 5.6B and the remaining phases. Reassess the independent adjudicator in 5.6C, align 5.7 delegated authority and notifications with workflow policy, and update Phase 6 plan orchestration and release criteria for the VM/worker topology and the simplified boundaries. Reassess earlier phase mechanisms where they constrain that work.

## Open questions for the operator

- What makes a PR eligible for automatic review, and which findings, CI outcomes, or scope changes require judgment in the first workflow policy?
- Which GitHub identities and completion or disposition signals should the controller accept for agent-published review evidence, including evidence edited or removed after observation?
- Does a durable webhook inbox still solve a demonstrated problem once startup, notification, periodic, and operator-triggered reconciliation share the same path?
- Which parts of the existing remote protocol are needed for explicit placement, observable outcomes, and conservative recovery?
