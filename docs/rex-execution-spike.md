# Phase C1 — Rex execution mechanism spike

**Recommendation.** Use Option B, the Rex CLI and a thin Switchyard executor. From `crow-ottoman`, the CLI launched commands on the Mac mini, recovered terminal evidence after a client died, and copied structured results. Both native providers started and continued disposable sessions. The offline Codex SDK crash killed its Rex child while the VM observer continued. The production access boundary and controller-owned recovery still need acceptance and verification in C2.

## Environment and connectivity

The spike started at Switchyard `636cb92` (PR #29). The Mac app bundled Rex `0.1.0-preview.25` (API 24), while the already-running personal server reported `preview.21` (API 18). The VM binary and its own server reported `preview.22` (API 19). The bundled Mac binary ran a disposable server with its own socket, state directory and empty config. The VM used its installed CLI for the first probes and a checksum-verified vendor `preview.25` Linux binary extracted into a temporary directory for file copy and native runs. The older VM CLI accepted lifecycle commands against the disposable server but lacked `cp`.

The Mac had active tailnet connectivity and a Rex peer. The VM had Tailscale installed with the service disabled and inactive. No working VM-to-Mac SSH route was established through the existing configuration. Rex documents `-S ssh://[USER@]HOST[:PORT][/SOCKET]` for a host already reachable by SSH. The [Rex-on-exe example](https://blog.exe.dev/rex) illustrates the opposite direction. [Rex remote access](https://www.superlogical.com/rex/docs/linux/remote-access) · [exe.dev networking](https://hub.exe.dev/docs/faq/cross-vm-networking)

With operator approval, the Mac opened a temporary OpenSSH reverse Unix-socket forward over its existing authenticated exe.dev connection. The VM socket was mode `0600` inside a `0700` directory. The Mac endpoint was the disposable Unix socket. VM processes used `rex -S unix://<vm-socket> --autostart=false` and verified the remote server's version before launch. A Mac child returned `Darwin arm64` and the requested working directory. This verified VM-originated execution with no per-command login. Access through the socket had the Mac user's execution authority. The tunnel used neither a TCP listener nor agent forwarding.

## Switchyard assignments and the A3 gate

The VM invoked the existing standalone CLI in a disposable Mac Git directory with Node 26.13.1, a fresh SQLite fixture and explicit assignment and execution IDs. Preflight in the Rex child confirmed ChatGPT sign-in for the SDK-bundled Codex CLI 0.171.0 and first-party subscription sign-in for Claude Code 2.1.332. The invocation cleared known billing and routing environment overrides and used the existing native profiles. Each provider completed a harmless schema-constrained start and one continuation, for four subscription turns total. A separate VM invocation supplied each continuation's logical session ID. Via `rex cp`, the VM verified the structured phrase, requested assignment and execution IDs, and the same logical and native session IDs for each continuation. All four reported completion and exited 0. The fixture DB supplied standalone CLI persistence for these tests.

The SDK regression used the [existing offline fixture](../test/fixtures/execution.ts). The spike launched the fixture's Node worker directly in a Rex block and reused its early-exit shell stub, which made no model request. With SDK 0.171.0 the process exited 1 with uncaught stdin `EPIPE` and empty stdout. The VM observer continued, read the same block's terminal evidence and launched recovery separately. The fixture DB retained the original execution as `running`. Recovery changed it to `unknown` once. A second recovery changed zero rows, re-claiming the execution did not dispatch, and another ID for the same assignment was rejected. The stub's launch marker stayed unchanged.

The tested process boundary can satisfy the crash-containment part of A3. The hold and no-replay behavior observed here came from the existing store on the Mac. The long-lived integration gate stays open until C2 proves the same behavior with a controller-owned claim on the VM.

## Phase C2 implementation scope

- **Placement and access.** Configure a named Mac placement with an explicit authenticated endpoint, compatible CLI and server versions, a validated working directory and native profile. For initial self-hosting, the tested reverse Unix-socket forward is viable if the operator accepts the VM controller identity's access to the Mac execution account. Make the tunnel reconnect independently of assignments and restrict socket access to the controller identity. The alternative is to authorize the VM on the existing tailnet with access scoped to a supported Mac Rex or SSH endpoint. That route and its identity policy remain unverified.
- **Lifecycle and result delivery.** Invoke the Rex CLI for launch, wait, inspection, interruption and copying. A small executor on the Mac runs one native turn in a separate process and publishes private, atomic execution metadata and structured results at a path keyed by the execution ID. Include assignment and execution IDs, terminal outcome and any native session ID. Carry the native reference in continuation requests. Keep a remote start marker that can be claimed once, and record the Rex block ID as supplementary evidence. There is no dependency on a permanent remote SQLite database.
- **Controller ownership and recovery.** Claim in the VM's SQLite before remote contact. On reconnect, reconcile the same attempt and validate its result against the claim and expected session. If launch acknowledgement was lost, look for the existing execution's evidence. Treat unreachable targets before dispatch as waiting and reserve `not_started` for affirmative non-execution evidence. Hold absent or conflicting evidence as `unknown` and block replay. Process exit or an acknowledged cancellation without a usable result leaves the native outcome unresolved.
- **Acceptance.** Demonstrate both providers and continuation through the actual controller. Verify lost launch acknowledgement, transport and child failure, recovery after controller restart, repeated result retrieval and targeted cancellation. Rerun the no-model A3 fixture while the VM holds the claim and confirm recovery without duplicate dispatch. Keep PR workflow decisions and approved-plan sequencing in Phases D and E.

Option A leaves Switchyard without the durable assignment-to-result record needed after process or terminal loss. Option B adds that record with a thin executor and uses the observed CLI capabilities directly. Option C is a fallback if authenticated Rex access or the required CLI behavior cannot be sustained. Reassess a small SSH-based executor at that point. The observed interfaces give no reason to build a TypeScript Rex client or restore the historical HTTP worker.
